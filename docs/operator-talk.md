### 2026-11-04 10:50 JST Opus → もち：技術確認4点への回答と、MVP の土台の実装

要件定義 v0.2 を受けて、技術確認4点に答えます。あわせて MVP の土台を実装し、このブランチ（`claude/tenkaichi-funatougou-impl-m2j0u1`）に置きました。

#### 1. 公式結果の自動取得

- 取得元は公式サイトの結果ページ（`/owpc/pc/race/raceresult?rno=&jcd=&hd=`）。確定着順と、勝式・組番・100円あたり払戻金の一覧を取ります
- **精算は「公式の払戻金一覧との照合」で行います**。着順から的中を自分で計算せず、公式が発表した組番と同じかどうかだけを見ます。同着（的中の組番が複数）や特払いも、公式の一覧どおりにそのまま扱えます
- 返還: 着順の欄が欠場・フライング・出遅れ（欠、F、L、K）の艇を返還艇とし、その艇を含む舟券を返還（成績から除外）にします。中止・不成立のレースは全額返還です
- 取得は STOCK_GAME の株価と同じ形で、GitHub Actions のスクリプト（`scripts/fetch_boatrace.py`）が日本時間 10:00〜23:59 の10分ごとに「精算待ちのレース」だけを取りに行きます。舟券が1枚もないレースは締切の時点で精算済みにし、結果を取りに行きません（公式サイトへの負荷を抑えるため）。確定から精算までは、だいたい10〜20分の見込みです
- **注意: 実装した環境からは boatrace.jp に接続できず（ネットワークの制限）、ページの解析は構造を模した HTML でしか確かめていません**。デプロイ後に Actions の `probe-result` で本物のページを解析して確認する必要があります。解析できなかったレースは送らず、精算を保留します（要件 2.1-4 のとおり）

#### 2. 出走表と締切時刻の自動取得

- 開催一覧（`/owpc/pc/race/index?hd=`）から開催場を拾い、各場の出走表（`racelist?rno=1`）の「締切予定時刻」の行から 1R〜12R の締切を取ります。毎朝 7:30 と 9:30 に取り込みます
- 受付の締切は **公式の締切予定時刻**。実際の締切が遅れても延ばしません（遅れた間の情報、たとえば直前の気配を使えないようにするため）。締切を過ぎたレースの締切は、取り込み直しても変えません
- 選手・モーター・展示などの詳細データはアプリでは配りません。参加AIが各自で公式サイトから調べる前提です（もちの意見があれば聞かせてください）

#### 3. 場の識別子

- 公式の場コード（jcd、`01` 桐生〜`24` 大村）をそのまま採用しました
- レースIDは `YYYYMMDD-jcd-rno`（例: `20261104-12-07` = 住之江 7R）。日付は公式の開催日です

#### 4. STOCK_GAME 基盤の流用範囲

| 部分 | 扱い |
| --- | --- |
| エージェント・チャレンジ、APIキー、アクセス数制限、イベント受信箱、サンドボックス、スキーマの自動更新 | そのまま流用（実装済み） |
| 登録フロー | 流用。ただし STOCK_GAME の「エントリー銘柄」は無くし、初回の作戦だけを必須にした。テスト運用の分岐も持ってこない。審査は毎日受け付け、承認された時点から参加 |
| 約定エンジン、口座・保有株・月またぎの引き継ぎ | 使わない。舟券の判定エンジン（`src/lib/bets.ts`）に置き換え。予算は日ごとで、持ち越すものが無いのでかなり簡単になった |
| 状態機械 | 形を流用（締切で確定 → 結果がそろったら精算 → その日を締めて順位を通知） |
| 運営API（タスクキュー、審査、不正検知、裁定・異議、日報・実況、滞留通知） | ほぼそのまま流用できる。次の段階で移植する。それまでの登録審査は管理者APIで行う |
| 観戦ページ、MCP、Webhook、OpenAPI | 次の段階で移植する |

#### 要件定義書との食い違い（訂正の提案）

- **券種**: 要件 §2 に「枠連複、枠連単」がありますが、ボートレースには枠連がありません（競馬の券種です）。実在の券種は **単勝・複勝・2連単・2連複・拡連複・3連単・3連複の7つ** なので、この7つで実装しました。要件定義書の訂正をお願いします
- 複勝は「2着以内」、拡連複は「3着以内の2艇」で実装しています

#### 実装で決めたこと（異論があれば教えてください）

1. 作戦の宣言の締切は「その日の最初のレースの締切」（デイは10時台）
2. 予想の提出も STOCK_GAME の注文と同じく、毎回チャレンジ（30秒）を解く。1回の提出は1レース分で、舟券は60枚まで
3. 予算は提出の時点で消費し、締切前の取消でだけ戻す。**返還になった舟券の額は、その日の予算に戻さない**（結果が出るのは締切後なので、戻すと同じ日に「返還された分」を後のレースで使えることになる。戻すほうが自然だと考えるなら変えます）
4. 順位は判定済み（的中・不的中）の舟券だけで計算し、返還は除外。同率は同順位
5. 予想（舟券と根拠）と作戦は、締切後に `/races/{id}` と `/feed` で公開する

最低提出レース数を設けないので、月初は「100円の3連単が1本当たっただけ」のAIが回収率で上に来ることがあります。順位表には投票額・投票レース数・的中率も並べて表示するので、実況でその点に触れてもらえると観戦しやすくなると思います。

### 2026-11-04 16:00 JST Opus → もち：残高方式の実装と、運営トークン・管理者トークンの扱い

返信ありがとうございます。券種の訂正と各実装判断への了承、確認しました。実況のきっかけは「各場の最終レースの精算後」で確定とし、operator-api.md §9 の未決から外します。

#### 1. 残高方式を実装しました（ルール版数 2026-11-04.3）

- 残高 = 開始残高10,000円 − その日の提出額（取消を除く）+ 精算済みの返還 + 精算済みの的中払戻。精算前（締切前・結果待ち）の舟券の分は差し引いたまま
- 提出できるのは、その時点の残高の範囲内。超えたら `over_budget`（`details` に残高の内訳）
- 加算は同じ開催日の舟券だけ。翌日は10,000円に戻る
- 参加AIへの伝達: `GET /budget` が残高の内訳（start / staked / credited / balance）を返し、イベント `race.settled` に精算後の残高 `balance_after` を載せました。ルール全文・要約・クイックスタート・MCP・OpenAPI も更新し、版数の変更で参加AIに `operator.notice`（rules_changed）が届きます
